# DSH Mobile architecture — initial implementation contract

## Decision and scope

Build a native Kotlin/Jetpack Compose Android app and a small optional in-process Cordis companion plugin for the existing DSH host. The plugin uses inspected DSH controllers; it does not scrape the web UI, export a browser launch token, replace DSH, or create a separate agent runtime. The Android app depends on our versioned mobile contract, not on DSH's internal wire format.

```
Android UI / ViewModel / repository
        | HTTPS + authenticated SSE
DSH Mobile host plugin: pairing, grants, command ledger, projection
        | direct in-process controller adapter
Existing DSH sessions / agent / persistence / tools / subscriptions
```

The raw DSH Web port remains unchanged and private. Direct invitation v1 remains the default transport and requires a reachable HTTPS route. An **optional built-in opaque relay transport v0.2** uses an operator-managed relay without an external phone VPN, home port forwarding or internet exposure of DSH. Deployments and phone acceptance require separate operator checks. Debug-only exact-loopback HTTP supports adb reverse for emulator acceptance.

Remote topology: Android → outer WSS → operator relay ← outbound WSS desktop connector → fixed loopback companion HTTPS. The relay forwards inner TLS bytes, not mobile API requests. Android uses a private authenticated CONNECT proxy accepting only `h-<32hex>.dsh.invalid:443`; normal inner certificate trust/date/exact-hostname validation and the mandatory SPKI pin stay end-to-end. Outer WSS uses separate public trust and route capabilities. The connector never accepts a peer-selected target. See [the authoritative relay contract](<RELAY_PROTOCOL.md>).

The relay can observe IPs, route/capability identifiers, timing, sizes and possible TLS handshake metadata; it can deny service. Device bearer and HTTP/chat contents remain inside verified inner TLS. Bootstrap access is replaced by a per-device relay grant after acknowledged pairing; it is never a permanent fallback. Phone credentials stay in encrypted local state. Transport retries do not replay command bytes or change receipt reconciliation.

## Ownership

- **DSH** owns actual sessions, messages, model execution, history and tool permissions.
- **Companion host** owns device grants, one-time pairing offers, revocation and command receipts. It exposes an explicit small set of operations; it is not a generic RPC proxy.
- **Android** owns presentation, paired-host credential storage, drafts and delivery-state UI. Closing an Activity only closes observation; it never cancels host work.

## Integration evidence

Installed DSH 0.2.0-rc.2 exposes `ctx.sessionController` with list/create/prompt/cancel/page/follow/projections. `follow` starts with a snapshot, then durable events and optional process-local assistant stream frames. Prompt carries a client requestId. Browser auth uses an authority-bound cookie derived from a launch token; no mobile auth grant was found. The stdio SDK creates a separate runtime and is not the integration for shared existing chats. The rc.4/rc.5 controller has the same mobile-facing methods; its additional `working-directory/change`, `job/registered` and `job/settled` durable facts are cursor-only and are not exposed in snapshots.

Evidence paths are documented generically under `node_modules/@deepseek-ai/dsh-api-session-controller/lib/types/` and `dsh-client-connection/lib/types/browser-auth.d.ts`; machine-specific absolute paths are deliberately not committed. Installed compiled JS and declaration files, not just package metadata, were inspected. Live composition remains an acceptance requirement. Adapter activation requires an explicit owner-declared DSH version from an exact allowlist of inspected releases (`0.2.0-rc.2`, `0.2.1-alpha.1`, `0.2.1-rc.4`, `0.2.1-rc.5`; see [SETUP](SETUP.md)) and refuses others before exposing observation/mutations. This declaration is not automatic host-version detection; the operator must revalidate after upgrading DSH.

## Quiet chat evidence and ownership

Read-only inspection of copied v4 journals (37 session files, concatenated Zstandard frames) found durable producer attribution in `user/message.data.source`, not special content block types. Across the inspected project sample: 41 `user`, 172 `agent-message`, 36 `subagent-settled`, 214 `tool-jobs`, 14 `compact-checkpoint`, 49 `runtime-context`, 89 `time-context`, 54 `agent-instructions`, 51 `skill-catalog`, 3 `plugin:hindsight` events. Content blocks for all these injections were ordinary `text`; `form` differentiated relay/notice/snapshot/instructions/catalog/recall where present. Counts describe this local evidence sample, not all DSH releases. Private journal copies/evidence remain outside the repository; fixtures contain only invented, redacted content.

Installed-source evidence: `dsh-llm/lib/types/message.d.ts` defines producer `kind` and semantic `form`; `dsh-subagent/lib/types/continuation-messages.js` stamps `agent-message` and `subagent-settled`; `dsh-agent-loop/lib/index.js` stamps `runtime-context`; `dsh-time-context/lib/index.js` stamps `time-context`; `dsh-compaction/lib/index.js` defines `compact-checkpoint`; `dsh-compaction-basic/lib/index.js` frames the exact checkpoint preamble; `dsh-tool-jobs/lib/index.js` stamps completion notices. Hindsight attribution was verified in copied journals, not inferred from its tag alone. Human messages have `source.kind:user`; request correlation is preserved independently of presentation.

Host projection is authoritative and additive: optional message `kind`/`serviceText` and optional snapshot `activityDetail`, validated and preserved at the HTTP/SSE boundary. Explicit human attribution preserves full text, without suffix extraction. Legacy extraction is lossless (`text + serviceText`), using a bounded monotonic scan on host and Android. Android derives immutable presentation copies off the composition thread; it never modifies delivery/reducer state. Local saved disclosure state uses an ordinary-message anchor (or history-start) and retains identities across overlapping history cuts. Consecutive service entries collapse between ordinary messages; tapping every compact preview, including context and extracted suffixes, opens selectable/copyable full text. The working indicator uses proven journal turn start and latest unmatched tool name when available, otherwise the last classified human message time. The fallback is intentionally conservative and cannot identify every future producer. This is information hierarchy, not a security redaction boundary. Full protocol rules and unchanged payload bounds are in [the protocol](<PROTOCOL.md#quiet-transcript-projection-additive-v1-extension>).

## Host security boundary

- Default bind is loopback. A non-loopback bind requires explicit TLS configuration. No insecure production fallback.
- Pairing is initiated by a local operator CLI. Offers use at least 256 random bits, expire quickly, are single-use, and are stored hashed. Successful pairing issues a separate random bearer credential scoped to one device; only its hash is stored on the host.
- A connection invitation includes server URL and certificate public-key pin, not a DSH credential. The Android client verifies the pinned host identity before sending the pairing secret. Standard hostname and certificate validity checks remain required.
- Tokens are never in query strings, logs, crash messages or SSE IDs. Device credentials are wrapped with Android Keystore and excluded from backup.
- A local SQLite state database provides transactional pairing consumption and a persistent command ledger. A separate stable adjacent SQLite lock database in non-WAL mode holds an exclusive transaction for the host lifetime, released by the OS on process exit; no PID-only stale-lock assumption. Acquire ownership before recovery/admission, release only after dispatches are settled or safely marked uncertain, and never unlink/replace the coordination file while an owner may exist. This is local-filesystem coordination, not a distributed/network-share locking claim. Credentials/configuration, certificates and the database stay outside Git. Use Node's built-in SQLite with a documented supported Node floor.
- Workspace source is owner-selected: legacy explicit `{id,name,path}` roots (default), or `workspaceSource:"dsh-registry"` with no nonempty explicit list. A shared live source calls `ctx.workspaceRegistry.list()` in durable sidebar order, maps DSH UUIDs/titles, caps the first 100 registrations, and omits missing directories entirely. Registry archive IDs are hidden from reads and mutations. Registry creation uses SessionController's inspected `workspaceId` lane to attach new sessions to the DSH sidebar; legacy explicit-list creation retains canonical `cwd` (the two upstream fields are mutually exclusive). Workspace identity is exact `fs.realpath` string equality, matching installed DSH even on case-sensitive Windows directories; no unconditional case folding. Listing deduplicates cwd resolution only inside one request (bounded to 1024 entries), so a later request cannot reuse a stale authorization binding. Snapshot headers and mutation paths resolve uncached. Adapter mutation admission also synchronously verifies that the observed registry revision is still current after filesystem preparation and cold iterator cleanup. After awaited directory status checks, the source verifies the same active underlying registry Service identity and exact visible IDs/paths/titles/order; concurrent changes fail closed rather than returning stale registrations. Cordis 4.0.4 produces fresh `ctx.get()` tracing proxies, so identity alone is normalized through its inspected `cordis.original` symbol, never by caching a proxy or bypassing the active lookup; method calls retain the traced caller context.
- An operator may explicitly choose **read and execute in all current and future DSH projects**. Local grants use `['*']` for each permission; execute `*` requires read `*`. Explicit grants remain supported in explicit-list mode, and execute must stay within read scope. The local `grant` command transactionally replaces only an active device's grants, not credentials, relay capabilities or receipts. Standalone registry-mode administration accepts `all` only and never reads DSH storage. No remote arbitrary cwd/path, settings changes, provider secrets, terminal proxy or arbitrary RPC access.
- **Workspace filtering is not a sandbox.** A trusted DSH agent may already have broader permissions and a transcript may contain cross-workspace material. The phone owner receives the permitted transcripts as-is. Do not advertise security isolation based only on cwd.
- Re-check authentication/grants for every request and periodically during streams. Host dispatch is the authorization linearization point: revocation blocks later admissions and closes observations, but does not retroactively cancel a command already dispatched to the trusted adapter (including its asynchronous preparation). The server passes its authorized `expectedWorkspaceId` into every adapter mutation; a fresh session mapping to a different registry ID is rejected before upstream prompt/cancel/create, independently of post-entry grant revocation semantics. Revocation/read-scope narrowing closes existing streams on periodic recheck (normally ≤1 s plus source I/O); execute-only narrowing republishes `canExecute:false` even while idle. Narrowing never retroactively cancels already-dispatched work. Body size, stream count, rate and pagination limits are bounded. Origin-bearing browser requests are rejected unless specifically supported; no permissive CORS.

## Delivery and recovery

Every mutation has a client-generated UUID requestId. The host stores (deviceId, requestId, operation, canonical payload hash, result/status) before dispatch. An identical repeat, including concurrent repeats, returns the same receipt; a different payload using the same identity returns 409. For message prompts, host plugin 0.7.0 passes DSH a per-device id derived from the requestId (see [Phone features](#phone-features-host-plugin-070)). Persist `dispatching` before touching DSH. On uncertain upstream outcome or a crash in the dispatch window, preserve `uncertain`; do not silently redispatch. DSH requestId reconciliation may strengthen this later, but no exactly-once promise is made across an unverified upstream boundary.

Android persists the requestId/draft before transmission and distinguishes sending, accepted, failed and uncertain delivery. A network timeout is not proof of failure. Reconnection looks up the original receipt and reloads the canonical conversation. Explicit uncertain-state UX prevents duplicate side effects. App 0.9.0 uses a fresh one-shot mutation connection, polls pending receipts automatically, consumes a create continuation once, and drains admitted sends independently of Activity backgrounding. A prompt may retry only after transport proof that no application headers were attempted (network failure, at most three attempts, same requestId); no uncertain replay or process-death outbox is added. Exhausted proven-unsent sends retain their draft and an explicit retry banner.

The host ledger has an identity and a monotonic epoch plus a small sidecar witness (`<statePath>.ledger.json`) containing the admitted/completed counters. A witness that observed more admissions or completions than the restored database proves a rollback; the host then opens in a recovery hold. The hold refuses fresh mutations before any dispatch with `recovery_hold` while keeping receipts, history and exact replay readable; the Android client treats that response as a proven pre-admission refusal (not-sent with the draft retained), never as uncertain. The operator reconciles evidence against DSH and releases the ledger with an explicit new epoch. Epoch rotation records a decision and is not evidence that old commands did not execute. Detection depends on the sidecar surviving the restore: restoring both files, or losing the sidecar, falls back to the documented manual hold/release procedure. The witness is best-effort local evidence, not a distributed ledger or an exactly-once guarantee.

The installed rc.2 follow implementation can promote a cold session after yielding its opening snapshot. Therefore observation must close the iterator after the opening frame; never advance a cold follow merely to observe. The adapter combines cold-safe opening snapshots with scoped host event subscriptions/periodic refresh, avoiding read-triggered model execution.

Observation uses SSE with a full bounded normalized snapshot first and subsequent replacement snapshots. On reconnect the client starts a new observation and replaces its view with an authoritative snapshot. This intentionally avoids pretending that an event cursor survives every plugin/host generation. History paging uses the corresponding DSH snapshot cut. Live assistant text is provisional until a durable assistant record replaces it.

A 100-message opening page is a raw-log suffix, not a self-contained surface. When its positional replacement cites an earlier node, the host uses inspected cold-safe `sessionController.page` reads backwards at the opening `throughSeq`, without advancing the follow iterator or activating an Agent. Recovery is limited to 16 pages including the opening and 16 MiB of serialized retained event records; each page still requests only 100 append-origin messages. Chronological contiguity and backwards boundaries are validated before merging; the complete combined fold is then trimmed to the latest 100 visible messages. Snapshot and notification evidence share this recovery path. If a long, compacted chat's dependency on an older replacement record cannot be resolved within these page/byte bounds, host plugin 0.7.0 no longer returns an empty message list: it keeps and returns the certain recent tail of messages with `hasMore:true` and the fixed history-cut notice, while obsolete/ambiguous messages remain suppressed. Newest contiguous turn/control events still determine activity when proven, independently of old surface ancestry. Unsupported required events, actual sequence gaps and oversized openings continue to fail closed. Notification completion evidence is never invented from an unresolved surface. Opening pages pass the same byte-admission check before surface/stream folding: oversized input yields no text, the fixed bounded notice, and only independently proven control activity. An upstream page is materialized in-process before its size can be checked, so the byte bound limits retained recovery records, not DSH's own log-read allocation.

Recovered immutable ancestry is reused in an LRU capped at 16 sessions and 32 MiB of serialized UTF-8 JSON, not heap usage; parsed objects, transient folds and upstream allocation are additional. Each request still authorizes a fresh canonical session/workspace binding and reads its cold opening; reuse requires the same current source revision/scope, a nondecreasing cut and exact raw-log overlap. An over-budget cached merge is discarded and recovery starts from the current opening; an exhausted result proves only the exact cut and bounded attempt, not a newer cut. Provider/scope changes, archived or removed sessions, `session/disposed` and adapter disposal evict entries. Per-session single-flight serializes recovery (at most 16 registered recovery sessions and 64 waiter registrations per session), with independently cancellable waiters; snapshots, watch refreshes and notification evidence share it. The last waiter leaving, scope/lifecycle invalidation and disposal detach a flight immediately even if upstream ignores cancellation. Abandoned work does not consume admission slots; late settlement cannot publish cache entries or disturb a fresh flight. Unchanged cuts and contiguous new events use the cached prefix without backward I/O. SSE admission validates the watch's first snapshot before sending headers and continues that same iterator, rather than reconstructing a second preflight snapshot. Notification queue drains reuse evidence by session/workspace through the proven cursor, keep fresh membership/source-revision checks and check each terminal against its own committed-answer proof; the drain-local map is capped at 256 sessions.

## Phone features (host plugin 0.7.0)

Host plugin 0.7.0 adds message delivery choice, queue actions, chat rename, model selection, answers to agent questions and skipping them, attachments and file downloads to API `/v1`. Each feature has its own capability flag next to `hostVersion`; older apps ignore the flags and newer apps hide features whose flag is absent. Routes, payloads and limits are in [the protocol](<PROTOCOL.md#phone-features-additive-v1-extension-host-plugin-070>). Host plugin 0.7.1 (`hostVersion:"0.7.1"`) keeps these features additively. It also records sessions accepted from the phone in an additive host-state table (schema 3→4, `mobile_created_sessions`) so that they stay in the session list while still blank (see [the protocol](<PROTOCOL.md#reads>)), and wakes the notification feed right after each committed journal update. That full-list-per-relevant-event behavior is historical. Current host plugin 0.9.0 uses fresh point lookups on notification and text-prompt hot paths, bounded per-session lanes with proof-capacity backpressure, independent stream heartbeats after the first page, and persisted degraded diagnostics. Notification fan-out reads an indexed `notification_settings` table of enabled, non-revoked devices; it no longer lists historical devices per source event. Full source-session lists remain for baseline/reconcile and legacy compositions without point lookup support.

- **Queue and steer.** A message is sent with DSH's own prompt mode `queue` by default: it is delivered on the next turn. An explicit steer uses DSH's prompt mode `steer`: the agent sees the message at its next step without stopping the current turn. A pending queued message can be steered now or removed from the queue on the computer. A message's `delivery` is reported only when the journal's inbox splice target proves it (next-turn → `queue`, next-step → `steer`). If the bounded history cannot prove it, the field is absent, and absence is not read as `queue`.
- **Model.** Snapshots, and their `session`, carry the model for the next model request, or `null` when the chat has no durable selection or request history; no default is substituted. List items carry it only when it is already available. A model selection takes effect when the next model request is built, possibly at the next step of the running turn; the request already running is not switched.
- **Questions.** Questions come from DSH's `ask_user_question` and are answered or skipped through DSH's user-questions service. Skipping the whole batch (`questionSkip`) sends an empty selection for each question upstream. The `recommended` option flag is derived from DSH's desktop "(Recommended)"/"(推荐)" label suffix convention; labels stay unchanged and are sent back verbatim. Snapshots list the last 20 settled calls as answered or skipped; DSH keeps no durable "expired" outcome. Legacy blocking questions without a call ID are not answerable from the phone.
- **Approvals.** Agent action approvals are not available to plugins and stay desktop-only.
- **Attachments.** Uploads are staged on the host, bound to the device, session and workspace, and expire after 10 minutes; cleanup runs every 30 seconds. The owning device can delete a staged upload unless an admitted send has already taken it. DSH's attachment service validates images at upload time; images stay in host memory until the send completes and count against the image budget for that whole time (staged, uploading and claimed by a send). Non-image files are written to the host plugin's private staging directory: outside any workspace, with random file names and owner-only access. They are uploaded to DSH's attachment store only at send time, right before the prompt. Abandoned or expired uploads never reach DSH. Staged files are deleted after the send (success or failure), on expiry, on plugin shutdown and by a startup sweep. Revoking a device from any host process, including the CLI, removes its staged uploads within 30 seconds or at its next request. Sent files go to DSH's own content-addressed attachment store, not into the project workspace.
- **Attachment limits.**
  - Uploads: 20 MiB per upload; 20 staged uploads per device and 64 per host.
  - Staging: non-image files ≤64 and ≤512 MiB in total, including in-flight uploads; images ≤200 MiB of raw bytes host-wide from upload until the send completes.
  - Rate: 2 concurrent uploads per device and 4 per host; 12 uploads per minute per device. The concurrency limits also cover the send-time upload to DSH, where the send waits for a free slot instead of failing.
  - Per message: ≤20 attachments and ≤200 MiB.
  - Send-time receipts: each attachment uploaded to DSH at send time holds a reservation, capped at 20 per session and 64 per host. The caps are counted per upstream file-upload service lifetime across plugin reloads and reset when DSH restarts, which also clears DSH's own unbound receipts. A plugin update with `install-host.ps1 -Upgrade -Activate` replaces the plugin block in the DSH profile with an unmounted placeholder, waits for the old listener to close and only then mounts the new version, which DSH hot-reloads. If the old listener does not close (for example, hot reload is not enabled), the installer stops at the placeholder without activating the new version; a coordinated DSH restart alone does not finish the upgrade, and activation of the new block must still be completed after the old listener stops (see [Setup](<SETUP.md#10-upgrade-rollback-revoke-and-uninstall>)). Slots reserved for a message but never used by an upload (for example, the send failed before uploading) are released immediately. An upload that was started stays reserved until DSH's public API proves the receipt retired (consumed or removed); an acknowledgement of the prompt alone does not release it. Before reserving, the host checks the reservations of all sessions (bounded to 64) and frees those proven retired.
  - Upgrade inventory: on a hot reload between host plugin generations (for example 0.7.0→0.7.1) the receipt budget is seeded from the feature-detected rc.2 `FileUploads.stagedFiles` WeakMap via live `ctx.sessions.list()` keys, but if that inventory cannot be proved or exceeds the scan bound, new file receipts are refused for that service lifetime rather than assuming zero prior receipts.
  - Admission: the reservation for all files of a message is made before the command is durably admitted. At most 16 message dispatches holding attachments run per host at a time. If either limit is reached, the request gets 429 before admission, no receipt is created, and the staged uploads stay available for a retry with the same requestId. Nothing is resent automatically.
- **Downloads.** Image and file downloads require only the read grant, and only for attachments whose referencing message is present in the snapshot the device actually receives (after the 2 MiB wire trimming).
  - Images: at most 2 concurrent downloads per device and 4 per host.
  - Files (`fileDownload`): ≤20 MiB and at most 2 concurrent downloads per host.
  - Attachment display names are truncated to 256 UTF-8 bytes at a code-point boundary instead of failing the snapshot.
- **Commands.** Each new mutation requires the execute grant for the session's workspace and uses the same durable receipts as other JSON commands; an exact replay of the same requestId, including concurrent replays, returns the original receipt, and uncertain delivery is not retried automatically.
- **Request IDs.** For message prompts the host passes DSH a per-device id derived from the mobile requestId, so two devices that pick the same requestId cannot collide upstream. Session create keeps the original requestId and cancel gets no derived id. Rename, model, queue and answer commands pass no requestId to DSH; it is used only in the host's receipt ledger. In GET and SSE snapshots a phone sees its own mobile requestId restored in `messages[].requestId` and `pendingQueue[].requestId` for its last 1024 prompt commands; IDs on other devices' messages are opaque. Prompts admitted by host plugin 0.6.0 keep their original IDs.
- **Transport.** JSON responses of 1024 bytes or more are gzip-compressed when the client accepts gzip; the 2 MiB JSON limit is unchanged and SSE is not compressed. The HTTP keep-alive timeout is 60 seconds.

Notification feed coverage reports `degraded` after a gap or overflow and returns to `ready` only after confirmed full recovery of all affected sources: no pending retry, overflow, unprocessed events or new errors in that pass.

## First release slice

Pair/import invitation, host connection status, workspace/preset selection, permitted sessions, bounded readable conversation history, new session, text prompt, live observation, stop active turn, reconnect/resync, local sign-out and remote device revocation. Native Material 3 UI, Russian/English resources, system light/dark, IME/safe-area support and font scaling.

## Explicit later capabilities

Attachments, image and file downloads and answers to structured questions arrived in host plugin 0.7.0 (see [Phone features](#phone-features-host-plugin-070)). Approval actions stay desktop-only because they are not available to plugins. Richer tool/subagent detail, push notifications (not implemented; the notification design uses no Firebase/FCM), multiple hosts and full offline history are separate slices. Capability negotiation must hide unavailable actions. Background notifications use a connection that the user enables explicitly and that runs in a foreground service with a visible persistent notification; there is no invisible background socket. Push is still not available, so no push delivery is claimed until a push path is configured and exercised.

## Validation gates

1. Public-boundary host tests: expired/reused pairing, unauthorized reads, revocation, read/execute grants, duplicate/mismatched command IDs, crash/uncertain semantics, bounded streams and reconnect snapshot.
2. Adapter fixtures reflecting inspected DSH event/projection shapes; compile/load compatibility with the installed Cordis API. Fixtures are synthetic and labelled.
3. Android unit tests for connection validation, pin enforcement, reducer/reconnect and delivery-state behavior; actual debug APK build and lint.
4. Emulator acceptance using an explicitly labelled fixture host, then isolated real DSH integration without changing active production settings. A fixture pass never counts as live DSH acceptance.
5. Independent security/correctness review and native screenshots in light/dark and increased font scale.
6. Physical phone Wi-Fi→mobile acceptance over the chosen direct HTTPS route or public opaque relay is a separate final gate requiring device/network access. v0.2 additionally needs wrong trust/pin/name/date, malicious relay/framing, grant publication/revoke/expiry, large JSON/long SSE, uncertain receipt and native release foreground/reconnect/resource-cleanup checks. Historical status for 0.8.1: on 2026-10-23 the 0.8.1 release APK was installed in place over 0.8.0 on a OnePlus CPH2747 with the same signing certificate, keeping app data and pairing; with host plugin 0.7.1 the app connected and synced the session list. Notification delivery under real Doze conditions has not been measured. Releases are no longer labelled a development preview.

## Rollout

[Remote setup](<REMOTE_SETUP.md>) prepares private state without activating the profile; [relay deployment](<RELAY_DEPLOYMENT.md>) governs an additive public service. Require independent review, live preflight, rollback protection and a canary for each rollout. Infrastructure permission does not imply permission to restart ongoing DSH work, reconfigure a home network or publish a repository. Release acceptance must identify the exact build and distinguish unit, fixture, emulator and physical-device results.
